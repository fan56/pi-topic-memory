为什么以前的注入，从来没有发生

扩展在 input 钩子启动异步 LLM 分类，耗时 5 到 15 秒。但 pi 在毫秒级就触发 before_agent_start，把上下文喂给模型。分类还没 settle，注入槽永远是 pending。绝大多数上下文注入扩展，其实从未真正注入。

毫秒级识别，零 LLM

同 topic 续聊不再调用 LLM。标题与来源的分词匹配加 Dice 系数即可高置信判定，叠加 tag 与同项目加分。

加分是纯加法，不混入 token 集合，Dice 分母不受污染。hasShared 守卫确保零重叠的 topic 永远无法靠加分越过门槛。

match.ts 
score = max(dice(input, title), dice(input, source)) + tokenMatch
if (hasShared) {
  score += 0.10            // PROJECT_MATCH_BONUS（同 cwd）
  score += 0.15 * tagHits  // TAG_MATCH_BONUS
}
return score >= 0.40       // MATCH_THRESHOLD，热路径与 LLM 路径共用

工程亮点

01

热路径免 LLM

~10ms

识别当前 topic 从 5 到 15 秒降到毫秒级。

02

tokenize / loadStore 缓存

每轮重复分词改走 LRU，每次读盘改走 mtime 内存缓存。

03

tags + 信息链

LLM 分类顺带抽取 tags，derivedFrom 记录父链，links 双向关联。

04

per-session 注入隔离

注入槽从全局单例改为 Map，按 sessionId 互不串扰。

Map<sessionId, slot>
05

/reload 自愈

session_shutdown 重置工厂哨兵，重载后扩展真正重新注册。

06

清除功能

删除 topic 连带清理 links 与 derivedFrom 引用，清空全部双重确认。

07

零丢失迁移

新字段经 normalizeTopic lenient 兜底，不 bump 版本号，现网台账原样保留。
